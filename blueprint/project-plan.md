# Project Plan

> Generated by `/adopt` from the existing codebase plus an intent interview,
> then reviewed and confirmed. This file is yours to own and edit. Re-run
> `/overview` after changing anything here.

## 1. Problem - What problem are we solving?

Youth Apostles members have no shared, current way to look each other up. Member
records already live in CiviCRM, but CiviCRM's own contact screens are an admin
tool: they are hard to navigate, expose far more than a member needs, and are not
something you hand to the whole community.

This plugin puts a clean, searchable directory on the organization's WordPress
site, reading live from CiviCRM so there is no second copy of the data to keep in
sync. A member can find someone by name or membership type, see how to reach
them, and print the whole thing for offline use.

## 2. Users - Who is this for?

**Members of the organization**, signed in to the WordPress site. There is one
audience and one permission level: any logged-in WordPress user sees the full
directory, including email, phone, mailing address, membership type, join date,
and family relationships.

This is deliberate, not an oversight. `check_permission()` in the REST
controller gates on `is_user_logged_in()` and nothing narrower, because everyone
with an account on this site is a member and is trusted with member contact
details.

There is no admin UI and no per-member privacy control. Who appears in the
directory is decided entirely in CiviCRM, by membership in group ID `27`.

## 3. Features - What does the MVP need?

The MVP has shipped. What exists today:

- Shortcode embed - `[youth_apostles_directory]` renders the directory into any
  WordPress page, and loads the built assets only on pages that use it
- Login-gated REST endpoint - `GET /wp-json/yamd/v1/members`, nonce-checked,
  logged-in users only
- Live CiviCRM read - APIv4 called in-process, no API key and no HTTP hop
- Member cards - photo or a placeholder avatar, name, membership type, clickable
  email and phone
- Search, filter, and sort - by name and membership type, all client-side over
  the full list
- Full-details modal - mailing address, member-since date, and relationships
  resolved from each member's own perspective
- Print view - a print stylesheet that hides the interactive chrome, reflows to
  two columns, and keeps cards from splitting across a page break
- Caching - a 5 minute transient so repeat page loads do not re-query CiviCRM

See `blueprint/build-plan.md` for what is shipped versus what is planned.

## 4. Data - What are we storing?

**The plugin stores nothing of its own.** No custom tables, no post types, no
options. CiviCRM is the single source of truth and the only writer.

Read from CiviCRM per member:

| Entity | Fields used |
|---|---|
| `Contact` | id, display_name, first_name, last_name, job_title, image_URL |
| `Email` / `Phone` | primary address and number (LEFT joins) |
| `Address` | street, supplemental line, city, state, postal code, country (primary only) |
| `Membership` | membership type label, join_date, end_date (active statuses only) |
| `Relationship` | directional type labels plus the related contact's display name |

The only persisted state is a WordPress transient, `yamd_members_cache`, holding
the assembled member list for 5 minutes.

Not yet mapped, and named in the build plan: chapter, vocation, community status,
community name. These are CiviCRM custom fields whose exact API names still need
to be found in the API4 Explorer.

## 5. Tech - What stack are we using?

| Layer | Choice |
|---|---|
| Host | WordPress plugin, in the same install as CiviCRM |
| Data source | CiviCRM APIv4, called as PHP in-process |
| Backend | Plain PHP, WordPress REST API, one controller class |
| Frontend | React 18 with hooks, mounted into a shortcode div |
| Build | `@wordpress/scripts` (wp-scripts), no hand-written webpack config |
| Styling | One hand-written `src/style.css`, `yamd-` prefixed classes, no framework |
| Dependencies | `react-modal` only |
| Package manager | npm (`package-lock.json`) |
| Types | None today. Full TypeScript migration is a planned build item. |
| Tests | None today. A unit test runner is a planned build item. |

This shape is intentional. Calling CiviCRM in-process instead of through its
external REST API means no API key to manage and no second network hop. Using
wp-scripts means React and JSX compile with zero build config, and WordPress's
bundled React is reused rather than shipped twice.

## 6. Monetize - How will this make money?

It does not. This is an internal tool for the organization's own members. There
is no billing, no subscription tier, and no advertising.

## 7. UI/UX - How should this look and feel?

Calm and utilitarian. A member should find a person in a few seconds without
being taught anything.

- **Layout** - filter bar, a member count with the print button beside it, then a
  responsive card grid (4 columns, 2 under 900px, 1 under 600px)
- **Card** - centered column: round avatar, name as the dominant element,
  membership, then contact lines, with the details button pinned to the bottom
- **Palette** - neutral grays on white, indigo (`#3730a3` on `#eef2ff`) as the
  single accent for interactive and emphasized elements
- **Feedback** - plain text states for loading and errors, no spinners
- **Print** - treated as a real output, not an afterthought

The card is the one part explicitly up for redesign. The next build item drops
the solid indigo membership pill and adds icons to the contact fields.

## 8. Deployment - Where and how will this ship?

**Zip upload through WordPress Admin.** There is no CI/CD pipeline and no server
build step.

The release path:

1. `npm install && npm run build` locally
2. Zip the plugin folder **including `build/`**
3. WordPress Admin > Plugins > Add New > Upload Plugin
4. Activate, then confirm the directory page still renders while logged in

Constraints worth knowing:

- `build/` is in `.gitignore`, so a clone of the repo is not installable on its
  own. The zip must be produced from a local build.
- The target site must already have CiviCRM active, with contacts in group `27`.
  The controller returns a `civicrm_missing` error rather than a blank page when
  it is not.
- No environment variables and no secrets. The Members group ID is a class
  constant in `includes/class-yamd-rest-controller.php`.
- No database migrations. Deactivating the plugin leaves no residue except an
  expiring transient.

Versioning is automated. `npm version patch|minor|major` bumps `package.json`,
then an npm `version` lifecycle script syncs the plugin header docblock and the
`YAMD_VERSION` constant and stages the plugin file, so all three land in npm's
version commit and tag together. Never edit the three by hand; they drift.
